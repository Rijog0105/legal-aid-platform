================================================================================
GENERAL UI PHILOSOPHY
================================================================================

The application is designed MOBILE FIRST.

The majority of users (Volunteers and Team Leads) will use the application
through their phones during legal aid camps.

The UI should require almost zero training.

A user should immediately know what action to perform after opening the app.

The interface should avoid:

- Complex menus
- Sidebars
- Nested navigation
- Dashboard clutter

Instead, every screen should expose only the actions required for that role.

Desktop versions should NOT redesign the UI.

Desktop should simply arrange the same cards in responsive grids.

PHOTO CAPTURE RULES
================================================================================

Each volunteer may upload a maximum of FIVE photos per activity.

The UI should always display:

Photos Used:
X / 5

The limit exists to:

• Reduce unnecessary storage
• Prevent spam uploads
• Reduce Faculty review workload
• Encourage volunteers to capture only meaningful documentation

FACULTY MODULE
================================================================================

The Faculty Module serves as the administrative control center of the platform.

Faculty members are responsible for:

• Managing the Permanent People Registry
• Creating and Managing Camps
• Assigning Participants
• Managing Activities
• Managing Budget
• Reviewing Documentation
• Reviewing Survey Data
• Preparing and Finalizing Camp Reports

The Faculty interface should prioritize simplicity and efficient workflows over
complex dashboards.

================================================================================
FACULTY HOME
================================================================================

After successful authentication, Faculty members enter the Faculty Control
Center.

The Faculty Home intentionally contains only two primary workspaces.

1. Camps
2. People Registry

All other operations are performed inside an individual Camp.

This keeps the application's hierarchy simple and reflects the camp-centric
architecture of the platform.

of the page while providing useful account information.

================================================================================
PEOPLE REGISTRY
================================================================================

The People Registry is a permanent database of all participants.

The registry exists independently of any Camp.

People are NOT created separately for each Camp.

The registry contains four categories.

• Guests
• Faculty
• Team Leads
• Volunteers

================================================================================
SELF REGISTRATION
================================================================================

Faculty members should not manually enter dozens of names into the registry.

Instead, the system provides a registration link.

Faculty
        │
        ▼
Share Registration Link
        │
        ▼
Participant completes registration form
        │
        ▼
Pending Approval
        │
        ▼
Faculty Accepts / Rejects
        │
        ▼
Permanent Registry

Guests are an exception.

Guest records are entered manually by Faculty since external guests generally
will not use the registration portal.

================================================================================
PENDING APPROVAL WORKFLOW
================================================================================

After registration, participants appear in a Pending Approval list.

Faculty reviews each registration.

For every registration Faculty may

• Accept
• Reject

When accepting a participant, Faculty assigns the participant's role.

Available Roles

• Volunteer (Default)
• Team Lead
• Faculty

Volunteer is pre-selected because most registrations are expected to be student
volunteers.

================================================================================
PERMANENT REGISTRY
================================================================================

Once approved, participants become part of the permanent registry.

Records remain available for future camps.

Participants are assigned to Camps from the registry.

The registry is never recreated for every new camp.

================================================================================
SEARCH AND FILTERS
================================================================================

The registry should support efficient searching.

Search

• Name
• Roll Number
• Email

Filters (Future)

• Batch
• Department

Roll numbers should be sortable in ascending and descending order.

This helps Faculty quickly locate active student batches while older graduated
batches remain archived in the registry.

================================================================================

The platform is CAMP-CENTRIC.

================================================================================
STARTING ATTENDANCE
================================================================================

Attendance can only be started by Faculty.

When Faculty selects "Start Attendance", the system first requests the Faculty's
current GPS location.

The Faculty does not need to manually enter the exact Camp address.

The Faculty only enters the general Camp location (Village/Area) while creating
the Camp.

The actual Attendance Location is captured live when Attendance begins.

Workflow

Faculty clicks

Start Attendance

↓

System requests Faculty GPS

↓

Faculty confirms detected location

↓

Attendance Session is created

================================================================================
ATTENDANCE SESSION
================================================================================

An Attendance Session stores

• Faculty Member
• Start Time
• End Time
• GPS Coordinates
• Attendance Radius

The Attendance Location is temporary and belongs only to that Attendance
Session.

================================================================================
ATTENDANCE RADIUS
================================================================================

Attendance verification is performed using the Faculty's live GPS location.

Default Radius

300 metres

Every Volunteer must be physically located within the Attendance Radius in
order to successfully mark attendance.

The radius may become configurable in future versions if required.

================================================================================
VOLUNTEER ATTENDANCE
================================================================================

Only participants who have accepted the Camp Invitation are allowed to mark
attendance.

Workflow

Volunteer opens application

↓

Attendance Session detected

↓

Press "Mark Attendance"

↓

System requests Volunteer GPS

↓

Distance from Attendance Centre calculated

↓

Within 300 metres

YES

↓

Attendance Recorded

NO

↓

Attendance Not Verified

================================================================================
ATTENDANCE STATUS
================================================================================

Each participant belongs to one of three attendance categories.

• Present
• Absent
• Invitation Pending

Definitions

Present

Participant accepted the invitation and successfully verified attendance within
the permitted Attendance Radius.

Absent

Participant accepted the invitation but failed to complete attendance before
the Attendance Session closed.

Invitation Pending

Participant never accepted the Camp Invitation and therefore could not
participate in Attendance.

================================================================================
DESIGN CONSIDERATIONS
================================================================================

Attendance is intended to verify physical presence at the Camp location.

The system intentionally uses the Faculty's live GPS location instead of a
manually entered Camp address because many Camps are created using only a
Village or Area name.

Using the Faculty's real-time GPS location provides a more accurate attendance
reference point.

================================================================================
CURRENT LIMITATIONS
================================================================================

The current MVP does not attempt to completely prevent credential sharing.

The design assumes that

• Faculty members are physically present during the Camp.
• Faculty are familiar with the participating students.
• Attendance is only one component of overall participation.
• Survey submissions and documentation provide additional evidence of
  participation when required.

This limitation is considered acceptable for the MVP and may be revisited in
future versions if stronger identity verification becomes necessary.

================================================================================
DESIGN PHILOSOPHY
================================================================================

The application follows a Camp-Centric architecture.

Everything belongs to a Camp.

The interface should prioritize simplicity while maintaining a premium visual
experience.

Design inspiration

• Apple Pages
• Apple Keynote
• Apple Numbers

UI Principles

• Rounded cards
• Soft shadows
• Smooth animations
• Colorful interface
• Right-side information panel
• Non-uniform widget layout
• Strong visual hierarchy

The Camp Workspace should avoid a traditional dashboard grid.

Instead, it should use an asymmetric card layout.

Camp Information occupies a larger vertical card.

Report Studio occupies a horizontal card beneath Camp Information.

All remaining workspace cards use equal dimensions and align perfectly within
the overall layout.

The layout should remain balanced without any overflowing or misaligned cards.
