# Phase 7 — Budget Module

> Official implementation documentation for the Budget Module of the Legal Aid Camp Management Platform.

---

## 1. Objectives & Scope

### Purpose
The **Budget Module** provides financial tracking, expense accounting, and institutional reporting capabilities for Legal Aid Camps. It enables Faculty Coordinators and Student Team Leads to track camp financial allocations, record line-item expenditure, analyze category-wise spending, and generate official institutional budget statements.

### Scope
- **Allocated Budget Management**: Setting and updating approved financial limits per camp.
- **Line-Item Expense CRUD**: Recording, updating, and deleting individual expenditure line items.
- **Financial Analytics & Dashboard**: 4 key financial metric cards and category-wise spending breakdown.
- **Standalone Budget Report**: Client-side PDF statement generation (`jspdf`) with domain-appropriate Legal Aid sign-off signature blocks.
- **Role-Based Workspace Integration**: Shared execution across Faculty Control Center and Team Lead Workspace.

### Module Responsibilities
1. Manage camp financial allocations (`allocated_budget`).
2. Maintain line-item expense records (`expenses` table).
3. Compute grand totals, remaining budget, and category breakdowns with safe non-NaN fallbacks.
4. Enforce strict RBAC controls across Faculty, Team Lead, and Volunteer roles.
5. Export standalone PDF budget statements with legal aid role signatures.

---

## 2. Architecture & Module Boundaries

### Ownership & Boundaries
- The **Budget Module** is self-contained within `src/features/budget/`.
- It owns the Allocated Budget UI, Expense CRUD, Financial Metrics, Category Breakdown, and the Standalone PDF Budget Report (`budgetReportGenerator.ts`).
- **Composite Report System Boundary**: The standalone PDF Budget Report is directly generated by the Budget Module. It **does not depend** on the composite Report Generator (Phase 8) or future Report Designer systems.

### Module Relationships
- **Camp Relationship**: Each `camps` record has one `allocated_budget` field and one-to-many associated `expenses` records (`camp_id` foreign key).
- **Faculty Relationship**: Faculty Coordinators have full administrative control, including setting `allocated_budget`, expense CRUD, and PDF exports.
- **Team Lead Relationship**: Team Leads have operational expense management access (Expense CRUD, PDF exports) while `allocated_budget` limit editing is restricted.
- **Volunteer Relationship**: Volunteers have zero access to the Budget Module or budget routes.

## 3. Implemented Features

### Financial Dashboard & Metrics
- **4 Key Metric Cards**:
  1. **Allocated Budget**: Approved financial allocation limit (`camps.allocated_budget`).
  2. **Total Spent**: Auto-computed sum of line-item expenses (`total_amount`).
  3. **Remaining Budget**: Computed difference (`Allocated - Total Spent`), with safe non-negative/non-NaN checks.
  4. **Expense Count**: Total number of recorded line items.

### Category Breakdown Grid
- Centralized `EXPENSE_CATEGORIES` constant (`Travel & Transport`, `Food & Refreshments`, `Printing & Stationery`, `Venue & Equipment`, `Honorarium & Fees`, `Miscellaneous`).
- Category cards showing category total spent, percentage of total spending, progress bar, and item counts.

### Expense CRUD & Modals
- **Allocated Budget Modal**: Zod-validated numeric modal for Faculty/Admin to set/update approved camp budget limits.
- **Expense Form Modal**: Zod-validated numeric modal for adding/editing expense items with live auto-computed total (`unit_cost * quantity`).
- **Search & Filtering**: Search bar filtering across description/remarks, and category dropdown filter.

### Standalone PDF Budget Report
- Client-side PDF generation using `jspdf` and `jspdf-autotable`.
- Formatted institutional statement containing Camp details, Financial metrics summary, Category breakdown summary, Itemized expense table, and Sign-off signature blocks (`Faculty Coordinator Signature` & `Student Team Lead Signature`).

### RBAC Controls
- `canEditAllocatedBudget`: `hasRole(['faculty', 'admin'])`
- `canManageExpenses`: `hasRole(['faculty', 'admin', 'team_lead'])`
- Volunteer access: Completely hidden and guarded.

## 4. Database Schema & Migration

### Schema Alignment (`supabase/migrations/003_budget_schema_alignment.sql`)
The database migration is 100% idempotent, safely handling fresh, partial, or existing databases using PL/pgSQL conditional blocks.

```sql
-- camps Table Addition
ALTER TABLE public.camps ADD COLUMN IF NOT EXISTS allocated_budget NUMERIC(10,2) DEFAULT 0.00;

-- expenses Table Definition
CREATE TABLE IF NOT EXISTS public.expenses (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  camp_id UUID NOT NULL REFERENCES public.camps(id) ON DELETE CASCADE,
  category TEXT NOT NULL DEFAULT 'Miscellaneous',
  description TEXT,
  unit_cost NUMERIC(10,2) NOT NULL CHECK (unit_cost >= 0),
  quantity INTEGER NOT NULL DEFAULT 1 CHECK (quantity > 0),
  total_amount NUMERIC(10,2) NOT NULL CHECK (total_amount >= 0),
  expense_date DATE NOT NULL DEFAULT CURRENT_DATE,
  remarks TEXT,
  receipt_url TEXT,
  created_by UUID NOT NULL REFERENCES public.persons(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### RLS Policies
```sql
CREATE POLICY "expenses_select" ON public.expenses FOR SELECT
  TO authenticated USING (public.get_user_role() IN ('admin', 'faculty', 'team_lead'));

CREATE POLICY "expenses_insert" ON public.expenses FOR INSERT
  TO authenticated WITH CHECK (public.get_user_role() IN ('admin', 'faculty', 'team_lead'));

CREATE POLICY "expenses_update" ON public.expenses FOR UPDATE
  TO authenticated USING (public.get_user_role() IN ('admin', 'faculty', 'team_lead'));

CREATE POLICY "expenses_delete" ON public.expenses FOR DELETE
  TO authenticated USING (public.get_user_role() IN ('admin', 'faculty', 'team_lead'));
```

## 6. Known Limitations

The following items are intentionally outside the scope of Phase 7 (Budget Module):
1. **Offline-First Synchronization Queue**: Direct Supabase operations are used for MVP. Dedicated IndexedDB offline mutation queues are deferred to post-MVP offline sync phases.
2. **Realtime Subscriptions**: State updates via local hook mutations and refetches; WebSocket real-time subscription listener is deferred.
3. **Narrative Sections**: 5 narrative section editors (Synopsis, Objectives, Observations, Recommendations, Conclusion) are pending in Phase 7.
4. **Composite Report Generation**: Multi-section composite document assembly (DOCX/PDF) is owned by Phase 8 (Report Generation).
